## Executive Summary

The **AI Revenue Recovery Agent** is an autonomous, bounded AI system that transforms raw payment failures into quantified revenue risk, diagnoses payment failure root causes, and executes strictly compliant recovery workflows to maximize recovered revenue ($\text{₹}$) for subscription merchants.

## 2. Core Philosophy: Why We Are Different

Legacy recovery tools attempt to solve involuntary churn by adding more retries. Our solution fundamentally re-architects recovery through three core engineering principles:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                         ENGINEERING PHILOSOPHY                           │
├──────────────────────────────────────────────────────────────────────────┤
│ 1. Diagnostic-First  : Shift from "When do I retry?" to "Why did it fail?"│
│ 2. Zero-Trust AI     : LLM Proposes ──► OPA Governance Gate Disposes    │
│ 3. Financial Truth   : Action ≠ Recovery (Settlement = Recovery)          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Diagnostic-First Recovery Paradigm
* **Traditional Approach:** "Payment failed. Retry in 24 hours, then again in 48 hours."
* **Our Paradigm:** "Payment failed. **Why did it fail?**"
  * If the failure is due to insufficient balance (NSF), retrying 24 hours later without payday context yields another decline. We align retry timing with customer salary cycles and bank processing windows.
  * If the failure is due to an expired card, retrying the same token is useless. We trigger an instant mandate repair workflow via a Razorpay Payment Link or mandate update flow.

### 2.2 Zero-Trust AI Architecture (LLM Proposes, OPA Disposes)
Generative AI and Large Language Models (LLMs) are uniquely suited for contextual reasoning, multi-channel messaging generation (e.g., Hinglish dunning prompts), and customer intent analysis. However, unconstrained LLMs pose catastrophic risks in fintech—hallucinating discounts, breaking retry velocity caps, or violating regulatory guidelines.

* **LLM Role (Proposal):** Contextual reasoning engine that evaluates failure metadata and proposes an optimal recovery action plan.
* **OPA Governance Role (Disposition):** A deterministic, isolated **Open Policy Agent (OPA)** guardrail. No action generated by the LLM can touch Razorpay APIs or customer communication channels without passing OPA compliance evaluation. If a proposed action violates RBI rules, cooldown periods, or merchant limits, OPA returns `deny` and forces a compliant fallback.

### 2.3 Strict Financial Settlement Principle: "Action $\neq$ Recovery"
In existing recovery engines, sending a dunning email or triggering an API retry is often logged as a "recovery attempt success." 

We enforce a strict accounting rule: **Action does not equal Recovery.**
* A recovery is recorded if and only if a transaction settles successfully ($\text{status} = \text{captured} \lor \text{status} = \text{settled}$) and money is deposited into the merchant's ledger.
* Every recovered rupee ($\text{₹}$) is cryptographically logged and reconciled against original payment failure IDs.

## 3. The 7-Step Solution Loop

The AI Revenue Recovery Agent operates as an event-driven, bounded execution pipeline spanning 7 deterministic stages:

```
 ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
 │ 1.INGEST │──► │ 2.RISK   │──► │3.DIAGNOSE│──► │ 4.DECIDE │
 └──────────┘    └──────────┘    └──────────┘    └──────────┘
                                                      │
                                                      ▼
 ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
 │ 7. AUDIT │◄── │6.EXECUTE │◄── │5. GOVERN │◄───┴──────────┘
 └──────────┘    └──────────┘    └──────────┘
```

### Step 1: Ingest (Razorpay Webhooks Engine)
* Listen for real-time Razorpay payment and subscription events (`payment.failed`, `subscription.halted`, `mandate.paused`).
* Normalize raw payloads into standardized event schemas containing gateway decline codes, payment method metadata, customer identifier, subscription plan value, and mandate registration state.

### Step 2: Quantify Risk (Revenue Risk Engine)
* Calculate real-time **Revenue at Risk ($\text{RaR}$)** for the ingested transaction.
* Assign dynamic recovery priority based on subscription LTV, historical payment reliability, and immediate rupee value at risk.
* Enqueue transactions into high-priority execution queues.

### Step 3: Diagnose (Deterministic Error Mapping)
* Map raw gateway error responses (e.g., `BAD_REQUEST_ERROR`, `GATEWAY_TIMEOUT`, `CARD_EXPIRED`, `INSUFFICIENT_FUNDS`) to a standardized diagnostic taxonomy:
  1. *Transient Infrastructure Decline* (Switch timeout, CBS offline)
  2. *Liquidity Friction* (NSF / Account empty)
  3. *Instrument Invalidation* (Card expired, account closed)
  4. *Mandate Compliance Lock* (Pre-debit notice missing, amount cap exceeded)

### Step 4: Decide (LLM Contextual Reasoning)
* Pass diagnostic telemetry and subscriber profile to the LLM Decision Engine.
* The LLM reasons over context parameters:
  * Optimal retry schedule (e.g., delay retry by $X$ hours until payday).
  * Intervention channel selection (e.g., Hinglish Voice recovery, WhatsApp payment link, email notification).
  * Incentive allocation (e.g., offer a grace period or small extension if allowed by merchant configuration).
* Output: A structured **Proposed Recovery Plan**.

### Step 5: Govern (OPA Regulatory & Guardrail Evaluation)
* Route the Proposed Recovery Plan to the Open Policy Agent (OPA) policy engine.
* OPA evaluates the plan against immutable RegTech policies:
  * *RBI Policy Check:* Has a 24-hour pre-debit notice been delivered prior to execution?
  * *Velocity Check:* Has the mandatory cooldown window between retries elapsed?
  * *Merchant Boundary Check:* Does the proposed discount/incentive exceed merchant caps?
* Outcome: `allow` (proceed to execution) or `deny` (fallback to default compliant action or halt).

### Step 6: Execute (Temporal State Machine Engine)
* Execute authorized recovery steps via durable, fault-tolerant state machine workflows (Temporal.io framework):
  * Call Razorpay Subscriptions API for automated retry execution.
  * Invoke Razorpay Payment Links API to issue manual settlement links.
  * Dispatch multi-channel dunning workflows via Novu communication orchestration (WhatsApp, SMS, Email, Voice).

### Step 7: Audit (Cryptographic Audit Ledger)
* Log all raw webhook inputs, diagnostic decisions, LLM prompt/response snapshots, OPA policy evaluation tokens (`allow`/`deny`), API execution responses, and financial settlement receipts.
* Persist audit entries into an append-only, tamper-evident cryptographic data store (`immudb`), providing Finance Controllers with 100% verifiable lineage for every rupee recovered.
