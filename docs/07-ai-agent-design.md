## Executive Summary

This document specifies the architecture, prompt context, structured output constraints, reasoning principles, observability, and fallback guardrails for the **AI Decision Agent**. Built on Large Language Models (Claude 3.5 Sonnet / OpenAI GPT-4o), the AI acts strictly as an untrusted decision engine. It proposes contextual recovery plans but possesses **zero direct execution authority**, requiring mandatory validation by the Open Policy Agent (OPA) Governance Gate prior to dispatch.

---

## 1. Agent Role & Boundaries (The Zero-Trust Principle)

In enterprise fintech architectures, unconstrained LLM execution presents severe regulatory, financial, and operational risks. Our design enforces a strict separation of concerns:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                     ZERO-TRUST AI BOUNDARY SCHEME                        │
├───────────────────────────────────┬──────────────────────────────────────┤
│ What the AI Agent DOES            │ What the AI Agent CANNOT DO          │
├───────────────────────────────────┼──────────────────────────────────────┤
│ • Analyze multi-dimensional state │ • Direct call to Razorpay APIs       │
│ • Predict optimal payday timing   │ • Direct call to Novu messaging      │
│ • Draft Hinglish dunning text     │ • Bypass RBI 24h pre-debit rules     │
│ • Propose structured recovery plan│ • Override merchant velocity limits  │
└───────────────────────────────────┴──────────────────────────────────────┘
```

1. **Decision Engine, Not Execution Engine:** The AI Agent's sole responsibility is contextual reasoning. It processes failure telemetry, subscriber history, and financial risk metrics to propose a structured recovery plan.
2. **Zero API Permissions:** The AI component is strictly isolated from external networks and credentials. It has no access to Razorpay API keys (`RAZORPAY_KEY_SECRET`), database write handles, or communication client tokens.
3. **Untrusted Payload Hand-off:** Every output generated by the LLM is classified as untrusted candidate input. The candidate plan is forwarded directly to the Open Policy Agent (OPA) for deterministic validation before any action occurs.

## 3. Structured Output Schema

The LLM is constrained via Pydantic / Instructor / OpenAI Structured Outputs to return a rigid JSON object. Unstructured free-form text output is rejected at the API interface.

```python
from enum import Enum
from typing import Optional
from pydantic import BaseModel, Field

class RecommendedActionEnum(str, Enum):
    SCHEDULE_RETRY = "SCHEDULE_RETRY"
    NOTIFY_CUSTOMER_UPDATE_PAYMENT = "NOTIFY_CUSTOMER_UPDATE_PAYMENT"
    ESCALATE_TO_HUMAN = "ESCALATE_TO_HUMAN"
    DO_NOTHING = "DO_NOTHING"

class ChannelEnum(str, Enum):
    WHATSAPP = "WHATSAPP"
    SMS = "SMS"
    EMAIL = "EMAIL"
    NONE = "NONE"

class ProposedRecoveryPlan(BaseModel):
    recommended_action: RecommendedActionEnum = Field(
        description="The primary recovery action proposed by the AI."
    )
    retry_delay_hours: Optional[int] = Field(
        default=None,
        description="Delay in hours before executing next retry attempt (Required if action is SCHEDULE_RETRY)."
    )
    communication_channel: ChannelEnum = Field(
        default=ChannelEnum.NONE,
        description="Channel for dunning communication."
    )
    dunning_message_text: Optional[str] = Field(
        default=None,
        description="Personalized dunning text (Hinglish/English)."
    )
    reason: str = Field(
        description="Plain-English explanation for audit logging."
    )
    confidence_score: float = Field(
        ge=0.0, le=1.0,
        description="Model confidence in proposed plan (0.0 to 1.0)."
    )
```

## 4. Core Reasoning Logic & Deterministic Principles

The LLM is guided by four foundational reasoning rules encoded in its system prompt:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                      REASONING STRATEGY MATRIX                           │
├──────────────────────────┬──────────────┬────────────────────────────────┤
│ Diagnostic Cause         │ Attempt Count│ Proposed Action Strategy       │
├──────────────────────────┼──────────────┼────────────────────────────────┤
│ INSUFFICIENT_FUNDS (NSF) │ 1            │ SCHEDULE_RETRY (Payday + 72h)  │
│ CARD_EXPIRED             │ 1            │ NOTIFY_CUSTOMER_UPDATE_PAYMENT │
│ SWITCH_TIMEOUT           │ 1            │ SCHEDULE_RETRY (Short + 4h)    │
│ Any Cause                │ 3 (Max)      │ ESCALATE_TO_HUMAN              │
└──────────────────────────┴──────────────┴────────────────────────────────┘
```

### Scenario A: Liquidity Friction (NSF on Attempt 1)
* **Context:** Cause = `INSUFFICIENT_FUNDS`, Attempt = 1, Payday = 23rd Aug.
* **Reasoning:** Retrying immediately or in 24 hours will hit an empty account and consume velocity quota. Delay retry by 72 hours to hit the salary credit window. Issue gentle WhatsApp dunning in Hinglish with an optional manual settlement link.
* **Proposal:** `recommended_action: SCHEDULE_RETRY`, `retry_delay_hours: 72`, `confidence_score: 0.94`.

### Scenario B: Hard Instrument Invalidation (Expired Card)
* **Context:** Cause = `CARD_EXPIRED`, Attempt = 1.
* **Reasoning:** API retries against an expired card token are mathematically guaranteed to fail ($P(\text{Success}) = 0$). Retrying wastes gateway fees and risks acquirer penalties. Automated retries are useless.
* **Proposal:** `recommended_action: NOTIFY_CUSTOMER_UPDATE_PAYMENT`, `communication_channel: EMAIL`, `confidence_score: 0.98`.

### Scenario C: Switch Timeout / CBS Downtime
* **Context:** Cause = `SWITCH_TIMEOUT`, Attempt = 1.
* **Reasoning:** Bank Core Banking System is experiencing transient downtime. The failure is uncorrelated with customer liquidity.
* **Proposal:** `recommended_action: SCHEDULE_RETRY`, `retry_delay_hours: 4`, `communication_channel: NONE`, `confidence_score: 0.91`.

### Scenario D: Maximum Attempt Exhaustion / High Uncertainty
* **Context:** Attempt = 3 or Confidence Score $< 0.80$.
* **Reasoning:** Maximum automated retry threshold reached without settlement. Continued retries risk regulatory blacklisting and customer harassment.
* **Proposal:** `recommended_action: ESCALATE_TO_HUMAN`, `confidence_score: 0.99`.

## 5. Deep Observability (Langfuse Integration)

Every LLM inference is wrapped with the **Langfuse SDK** to provide 100% observability over AI decision-making.

```
┌──────────────────────────────────────────────────────────────────────────┐
│                      LANGFUSE OBSERVABILITY PIPELINE                     │
├──────────────────────────────────────────────────────────────────────────┤
│ System Prompt + Context Payload                                          │
│ └── ► LLM Inference Execution                                            │
│     └── ► Extract Trace Metrics:                                         │
│         • Trace ID: trc_langfuse_9988776655443322                        │
│         • Prompt Tokens: 842 | Completion Tokens: 165                   │
│         • Total Cost: $0.0031 USD | Latency: 620ms                      │
│         • Saved to PostgreSQL & Hashed to immudb                         │
└──────────────────────────────────────────────────────────────────────────┘
```

### Trace Metadata Captured
* `trace_id`: Unique identifier generated per inference call (`trc_langfuse_<uuid>`).
* `prompt_template_version`: Version of system prompt used (`v1.4.2`).
* `input_payload`: Complete JSON prompt string injected.
* `output_json`: Raw structured JSON output.
* `latency_ms`: Total round-trip inference latency (Target SLA: $< 1500\text{ms}$).
* `token_usage`: Input tokens, output tokens, total cost in USD.
* `immudb_link`: The `trace_id` is written directly into the `immudb` audit record to guarantee cryptographic linkage between AI reasoning and financial settlement.

## 6. Fallbacks & Guardrail Enforcement

If the LLM fails or exhibits erratic behavior, the system automatically falls back to deterministic safety routines:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                       FALLBACK DECISION TREE                             │
├──────────────────────────────────┬───────────────────────────────────────┤
│ Failure Mode                     │ Fallback Action                       │
├──────────────────────────────────┼───────────────────────────────────────┤
│ Inference Timeout (> 3000ms)     │ Deterministic Static Rules Engine     │
│ Pydantic Validation Error        │ Deterministic Static Rules Engine     │
│ Low Confidence Score (< 0.80)    │ Force Action: ESCALATE_TO_HUMAN       │
│ OPA Governance Denial            │ Abort Workflow ──► Human Review Queue │
└──────────────────────────────────┴───────────────────────────────────────┘
```

1. **Inference Timeout ($> 3000\text{ms}$):** If the LLM call times out, Temporal catches the exception and routes payload execution to the **Deterministic Rules Engine Activity** (applying standard 48-hour retry defaults).
2. **Schema Validation Failure:** If the output violates `ProposedRecoveryPlan` Pydantic validation (e.g., hallucinated enum value), the raw response is logged to Langfuse as an anomaly, and the deterministic fallback is triggered.
3. **Low Confidence Floor ($< 0.80$):** If `confidence_score < 0.80`, the AI's proposal is rejected automatically and replaced with `recommended_action: ESCALATE_TO_HUMAN`.
